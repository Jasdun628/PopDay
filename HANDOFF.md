## Architecture (as built)

One source adapter per market; everything downstream market-agnostic:

- `popday/sources/__init__.py` — the common `Announcement` dataclass (source, market, dedup_key, company_name, company_identifier, headline, wire_or_form, announced_at UTC, detail_url, raw_text).
- `popday/sources/investegate.py` — UK adapter: `InvestegateClient` with `index_for_date()` (full day index, `perPage=300`, pages until short page), `scan()` (headline matches only, detail text fetched only for matches), `probe_canary()` (pinned Glencore CMD announcement), `InvestegateBlockedError` (403/429-after-backoff/Cloudflare-challenge-by-body-signature), robots.txt checked at construction (`InvestegateRobotsDisallowedError`), 2s minimum request spacing (floored).
- `popday/sources/edgar.py` — thin wrap over `popday/edgar_fetch.py` (`EdgarSource.scan()/probe_canary()`, `announcement_from_filing()`). **Honest limitation:** `cli.py`'s US path still consumes `Filing` natively (it needs the SGML envelope richness); the wrap exists for uniform orchestration and future convergence, documented in its docstring.
- `market` column (`'US'`/`'UK'`, default `'US'`) on detections, processed_filings, known_announcements, hype_tracking, price_reactions; `source` column (default `'edgar'`) on scan_runs. New tables `prices` (UNIQUE(ticker,date)) and `ticker_mappings` (manual_override column wins over derived symbol).
- Detection: `popday/detector.py detect_in_uk_announcement()` — reuses `split_sentences` + `extract_event_date` verbatim (no forked logic; they were already generic, so no refactor of the US path was needed). UK-specific: word-boundary phrase matching (so `cmd` never matches "recommend"), headline-match counts as announcement context, TBD path when the headline announces but no date parses. `Detection` gained `market` and `ticker` fields (defaults preserve US behaviour byte-for-byte).
- CLI: `popday.py --source investegate --date previous-business-day` runs the UK scan; `--source edgar` (default) is the unchanged US path. `--market US|UK` filters `--reclassify`. Per-source: coverage sweep (`covered_ok_dates`/`earliest_ok_run_date` take a source), ops-alarm keys (`scan_failure:investegate`, heartbeat `heartbeat:investegate`), canary control, self-healing backfill (UK backfill = the same scan pointed at archive day pages, which are the same URL shape as today's page).
- Hype (Phase 1b): `popday/hype.py update_uk_hype_from_index()` — runs inside each UK scan against the already-in-memory day index; counts non-routine announcements (config `uk_routine_headlines` exclusion list) from companies with open UK events, window (announcement, event]; appends to `detected_json` in the US shape, deduplicated on the numeric ID, so `qualifying_count` and `--reclassify` work identically across markets. `reclassify_hype_tracking` preserves each row's market (regression-tested).
- Prices (Phase 2, capture only): `popday/prices.py` + `scripts/capture_uk_prices.py`. EPIC→Yahoo mapping (`VOD→VOD.L`, `NG.→NG.L`, `BT.A→BT-A.L`) recorded in ticker_mappings; GBp÷100→'GBP'; never FX-converts; window [announcement−14cd, event+14cd] (≈10 trading days each side, erring generous — capture-only); failures logged non-fatal, upserts heal gaps. Suggested PA task: 20:30 UTC daily (checkpoint 3 gates creating it).
- Web UI: market pill row `All | US | UK` (`?market=`) on Investor Days, Research/Hype, Price Reaction, Scan Log; carried through all sort links. UK rows link out to Investegate detail pages (source_type CASE in the SQL; `_prepare_row`'s non-EDGAR passthrough). £/$ per row from market. **Never renders Investegate body text** — snippets are our own extracted nugget sentences only, per their personal-use terms.
- Email: one combined daily digest, grouped by market with section headers (`US - SEC EDGAR` / `UK - RNS (via Investegate)`) ONLY when a batch spans both markets; single-market emails (all existing traffic) are unchanged, regression-tested.
- Health: per-source `sources` block in status JSON (`scan_health` + `coverage_health` per source); headline health = worst across sources; flask banner evaluates per-source (UK banner prefixed "UK scan:"); heartbeat loops sources with ≥1 ok run (a never-launched source can't false-alarm). `_assess_coverage` treats `investegate-index` like `efts` (zero matches is normal; only `daily-index` treats all-zero as breakage).

## Email extraction fixes (2026-07-15, unrelated to the UK build)
Two small bugs found in a live alert (the Ligand one), both fixed in `popday/detector.py` and `popday/emailer.py`, 4 new tests, no schema/deploy changes needed.

- **IR link picking up XBRL taxonomy URIs.** `_best_event_url()`'s scoring treated any URL/text containing "presentation" as a real investor-presentation link — including `http://www.xbrl.org/2003/role/presentationLinkbaseRef`, since "presentation" is a substring of "presentationLinkbaseRef". Added `_is_taxonomy_junk_url()`: hard-excludes (before scoring, not just a score penalty) any URL whose host is `xbrl.org`/`fasb.org`/`sec.gov`/`w3.org`/`xbrl.sec.gov` (or a subdomain), or whose path contains `/role/` or `/linkbase/`. If nothing survives the filter, `event_url` is `""` and the "COMPANY EVENT / IR LINK" section is correctly omitted from the email (existing `if event_url_raw:` guard) rather than showing a wrong link.
  - **Deferred (per brief, non-goal):** a real IR-domain-by-ticker fallback lookup, so a filing with no usable link at all could still surface *something* useful. Would need a ticker→IR-domain data source (not currently in scope/available) - noted here as the natural next step if this keeps happening on filings with no real link anywhere.
- **Main Nugget duplicating Key Excerpt.** Both fields derived from the same narrow `Detection.snippet` (one sentence), so on short press releases they printed near-identical text. `Detection` gained a `context_text` field (the full press-release/cover-page text the snippet was drawn from - not persisted to the DB, only used for same-run alert building) populated in `_best_event_signal`/`_best_tbd_signal`/`detect_in_uk_announcement`. `_main_nugget()` now: locates the Key Excerpt's source sentence within `context_text` (`_find_anchor_index`, exact-or-truncated-prefix match, since `snippet` and `context_text` come from the same `split_sentences()` call over the same text), searches ±2 neighboring sentences for one containing a number/date/context marker (`_has_context_marker`: any digit, or a small keyword list - spin-off, inaugural, first-time, headquartered, outlook, guidance), and suppresses the result if it's >90% token-overlap similar to Key Excerpt (`_token_overlap_ratio`, a similarity-guard backstop). No context, no anchor, or no qualifying distinct sentence → Main Nugget is omitted (`""`), same "blank is honest" principle as the IR-link fix. Legacy `detect_in_sections` path and known-announcement entries have no `context_text`, so they correctly get no Main Nugget rather than a guessed one.

## `known_announcements` — what it's for, and the Sandisk "blank everywhere" resolution (2026-07-15)

**What `known_announcements` is.** A second, much smaller announcements table alongside `detections` (the EDGAR-scan-populated one), for events PopDay's own scan will never find: press-release-only announcements that were never filed with the SEC at all. It's read into the same UNION queries as `detections` (`investor_day_announcements()`, `research_hype_events()`, Price Reaction), so a row here shows up on every public tab exactly like a real EDGAR detection does. There is **no code path that writes to it** - `db.add_known_announcement()` exists but has zero callers anywhere in the codebase. Every row is added by hand (raw SQL), and its `notes` column is expected to say so. As of this writing there are exactly two rows: Radian Group Inc. (added 2026-06-04) and Sandisk Corp (added 2026-07-14).

**Why a blank-everywhere row isn't necessarily a bug.** `known_announcements` has no CIK column, by design - these events never touched EDGAR, so there's no CIK to store. That means:
- Ticker/price resolution has always depended on a hardcoded `COMPANY_TICKER_OVERRIDES` dict in `popday/stock_reaction.py`. Radian was in it (`RDN`); Sandisk wasn't, hence "no ticker found."
- Hype/investor-comms counts for *any* `known_announcements` row (Radian included, not just Sandisk) are permanently unavailable - they're computed by querying SEC's own filing feed by CIK, which structurally cannot exist for a press-release-only event. This is not a bug to fix; it renders as "—" on the Research/Hype tab, which is honest.

**The fix (this brief).** Added `ticker_override`/`cik_override` columns directly on `known_announcements` (same manual-override pattern as the UK `ticker_mappings` table), surfaced through `investor_day_announcements()`'s known_announcements branch aliased straight onto `cik`/`ticker` - `resolve_ticker()` already checked those fields before falling back to the hardcoded dict, so no logic changes were needed there. `research_hype_events()` already resolves `known_announcements` tickers via its own `price_reactions` JOIN (from the earlier Bug 7 fix), so it inherited this fix automatically. Backfilled Sandisk's `cik_override` to its real SEC CIK (2023554) directly on the live DB - same manual-entry pattern as the row itself. Confirmed live: Sandisk now shows ticker `SNDK` and real price/reaction data; Radian and all EDGAR-sourced rows unaffected (spot-checked several, all still resolve correctly).

**Deliberately not done:** extending hype classification (`watch_hype_candidates`) to cover `known_announcements` rows. `hype_tracking.candidate_id` is a bare primary key implicitly assumed to be a `detections.id` - `known_announcements` has its own independent id sequence starting at 1, and `detections.id=1` is a real, unrelated row (Henry Schein Inc). Wiring the two together as-is would silently corrupt `hype_tracking` for whichever `detections` row happens to share an id with a `known_announcements` row. Doing this safely needs a namespaced key (mirroring how `price_reactions.announcement_key` already disambiguates via a `"source_table:id"` prefix) - flagged as a real gap, not attempted here.

**Takeaway for future "why is this row blank" questions:** a `known_announcements` row showing populated ticker/price but blank hype counts is expected and correct, not a bug. A `known_announcements` row showing *everything* blank almost certainly means its `ticker_override`/`cik_override` was never backfilled - check those two columns before assuming a pipeline bug.

## Deploy failure recovery + hardening (2026-07-15)

The auto-deploy gate (`scripts/auto_deploy_gate.sh`, runs 2x/day via launchd from `~/PopDayAutoDeploy`) alarmed that `deploy_dev_to_pythonanywhere.sh` exited non-zero for commit `e37c47c` ("exited non-zero ... after its own internal retries. GitHub has the new code, but PythonAnywhere may still be running the previous version - check manually").

**What actually happened.** Checked PA directly (file content, mtimes, and both live verifier scripts re-run clean): the code was already fully and correctly deployed - the site was never broken. Found the real cause in the launchd log (`~/PopDayRuntime/logs/popday.autodeploy.{out,err}.log`): the deploy script's code-sync (scp) and Price Reaction cache refresh both completed successfully, then the very next step - `generate_status_json.py`, run over SSH - hit `Connection closed by ... port 22` (a transient network blip) and the script aborted immediately under `set -e`. It never even reached the reload/live-verification step, despite the actual deploy having already succeeded minutes earlier. The alarm text ("after its own internal retries") was itself misleading - the script's only retry loop (`POPDAY_DEPLOY_VERIFY_RETRIES`) was never reached; there was no retry at all around the step that actually failed.

**The design bug this exposed:** `generate_status_json.py`'s SSH call had no `|| echo WARNING...` fallback, while the *structurally identical, sibling* `refresh_price_reaction.py` call one line above it did - both are explicitly commented as "belt-and-braces... non-fatal," but only one actually was. A transient blip in either one shouldn't be able to abort a deploy whose real code sync already landed.

**Fix - `scripts/deploy_dev_to_pythonanywhere.sh`:** every major step now calls a `step()` helper to name itself, and an `ERR` trap (`set -Eeuo pipefail` + `trap ... ERR`) prints `DEPLOY FAILED AT STEP: <name> (line N, command: ..., exit N)` on any failure - a specific, actionable message instead of a bare non-zero exit. Gave `generate_status_json.py` the same non-fatal guard `refresh_price_reaction.py` already had, closing the actual gap that caused this incident. No retry logic changed - `POPDAY_DEPLOY_VERIFY_RETRIES` and its backoff are untouched.

**Fix - `scripts/auto_deploy_gate.sh`:** now captures the deploy script's output (still streamed live via `tee`, so the launchd log keeps the full transcript) and extracts the `DEPLOY FAILED AT STEP:` line into the ops-alert email body, with a clear fallback message if the deploy script fails some other way (e.g. killed by a signal) than through its own trap. The alerting itself was already correctly wired (via the same `ops_alerts` state machine and cooldown/recovery behaviour scan failures use, `popday/db.py`'s `check_and_update_ops_alert`) - this only makes the *message* specific.

Verified with a deliberate, safe test failure (bad SSH hostname, run locally against the real script - never touched GitHub or real PA): confirmed the trap fires with the exact failing step/command/exit code. Separately verified the log-capture/extraction logic in `auto_deploy_gate.sh` against a stand-in script for both the marker-found and marker-missing cases. Then closed the loop for real: pushed and ran the actual hardened deploy script against PA - clean pass, both live verifiers green.

## Deploy gate wedged on a persistent data-curation check (2026-07-17)

The auto-deploy gate alarmed repeatedly (3 retries × 2 scheduled runs) that `deploy_dev_to_pythonanywhere.sh` failed live verification for commit `b52d678` - a **docs-only** commit (+14 lines to this file, no code), which made it structurally impossible for the commit itself to be the cause.

**Root cause.** `scripts/verify_live_popday_buttons.py`'s "Investor Days company names are linked" check required *every* company name on the live Investor Days page to resolve through `DEFAULT_COMPANY_WEBSITES` (`popday/config.py`) to a real link - but that dict is a hand-curated list that is only ever updated in batches (see the "Added 7 Jul"/"Added 15 Jul" comments already in it), while daily scans surface new companies continuously. The 16 Jul 2026 04:00 UTC scan detected three new Investor Day companies - ASML Holding NV, Hanover Insurance Group Inc., Smith & Wesson Brands Inc. - none yet curated, so this one check failed on every deploy attempt from that point on, regardless of what the deploy actually shipped. Confirmed via the launchd deploy log (`~/PopDayRuntime/logs/popday.autodeploy.out.log`): all 22 other assertions in both verifiers passed cleanly on every attempt; only this one ever failed.

**The design bug this exposed:** a per-row data-completeness metric was wired into the deploy gate as a blocking pass/fail check. Any future newly-surfaced, not-yet-curated company can and will trip this same check again, potentially blocking an unrelated, fully correct commit indefinitely - exactly the failure mode hit here.

**Fix - `scripts/verify_live_popday_buttons.py`:** the company-link check is now advisory (`check_advisory()`, prints `WARN` rather than `FAIL` and never enters the `failures` list that gates the exit code). It stays visible in every deploy log, so a real curation gap is still noticed - it just can no longer block shipping code. **Standing rule: the deploy gate may only assert "is the app serving correctly" (pages return 200, expected structure/labels present, buttons work). Any check whose truth depends on the current state of scanned/curated data - not on the code being deployed - must be advisory, never blocking.** Data-quality gaps belong in System Health / ops-alert monitoring, not the deploy gate.

**Fix - `popday/config.py`:** curated real, verified URLs for the three newly-surfaced companies (ASML → asml.com, Hanover Insurance Group → hanover.com, Smith & Wesson Brands → smith-wesson.com), clearing the actual gap the check had (correctly, if too bluntly) surfaced.

**Investigated and ruled out as unrelated:** the live homepage's `ADIG` "Could not fetch daily prices... HTTP Error 404" row (Legacy Price Reaction table). Confirmed via web search: ADI Global Distribution is spinning off from Resideo and does not begin regular-way NYSE trading under ticker `ADIG` until 4 Aug 2026 - Yahoo Finance naturally 404s for a ticker that isn't trading yet. Not a bug, no fix needed; self-resolves on/after 4 Aug 2026. This condition does not appear in either verifier's assertions and was not the deploy blocker.

**PA checkout:** confirmed via SSH to be running byte-identical code to `origin/main` at the time of diagnosis - ruled out as a cause. Both verifier scripts also passed 100% when run manually against the live site before any fix, except for the one company-link check - confirming the failure was isolated to that single assertion, not a broader outage (the site was never down or degraded for visitors).

**Cleared the backlog:** pushed both fixes (`fb6a9c0`, `08b881e`), then ran `scripts/auto_deploy_gate.sh` for real from `~/PopDayAutoDeploy` (the same entry point and env vars launchd uses) rather than just the inner deploy script, so the ops-alert state machine would resolve itself exactly as it would on a real scheduled run. Result: full test suite green (148/148), fast-forward pull, deploy, both live verifiers green on the first attempt (no retries needed), exactly one recovery email sent, `.last_deployed_commit` marker updated to `08b881e`. Confirmed scan coverage was never affected: EDGAR and Investegate scans both show `status='ok'` for every business day since 15 Jul, including the 16 Jul run that surfaced the three new companies - the site was serving fresh, correct data throughout; only the *deploy pipeline*, not the live product, was stuck.

## Admin login lockout diagnosis + password reset flow (2026-09-04, NOT YET DEPLOYED - checkpoint pending)

**Diagnosis.** The admin credential lived nowhere but the `POPDAY_ADMIN_PASSWORD` env var, compared with `secrets.compare_digest()` in `flask_app.py`'s `admin_login()` - no hash, no DB row, no config.json key. **Fix - moved the credential off the single env var, into the DB, with a self-service reset path (`popday/db.py`, `flask_app.py`, `templates/admin_forgot.html`, `templates/admin_reset.html`).** New `admin_auth` table (single row: `password_hash`, `reset_token_hash`, `reset_token_expires_utc`). `admin_login()` now checks a `werkzeug.security` pbkdf2 hash (`check_password_hash`) stored in that row rather than comparing the env var directly; `_get_admin_password_hash()` lazily bootstraps the DB hash from `POPDAY_ADMIN_PASSWORD` the first time it's read if no hash exists yet, so nothing breaks for any deployment that never touches this feature. `app.secret_key` (session-cookie signing) deliberately left untouched - still derived from the env var at import time - so a password reset doesn't invalidate the signing key or unrelated sessions.

**This is also the actual unlock mechanism for the current lockout:** once deployed, Jason doesn't need to know or recover whatever is currently set on PA - "Forgotten password?" -> check the email `config.json`'s `email_to` points to -> set a brand-new password, done.
